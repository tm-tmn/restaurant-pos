# Restaurant POS

ระบบ POS สำหรับร้านอาหาร — **Phase 1: Core POS ✅ · Phase 2: Inventory & BOM ✅**
React PWA (ใช้งานต่อได้เมื่ออินเทอร์เน็ตขัดข้อง) + NestJS API + PostgreSQL

> ขอบเขตปัจจุบันยังไม่รวมการเชื่อมต่อ GrabFood / Delivery (ตัดออกตามแผน)

## ฟีเจอร์ใน Phase 1

| ส่วน | รายละเอียด |
|---|---|
| ขายหน้าร้าน | Quick Scan ด้วยเครื่องสแกนบาร์โค้ด (USB/Bluetooth), ค้นหาเมนู/SKU, หมวดหมู่, ตะกร้าคงอยู่แม้รีเฟรช |
| โต๊ะ | ผังโต๊ะ, เปิดบิล, เพิ่มรายการเข้าบิล (ส่งครัว), 1 โต๊ะ 1 บิลเปิด (กันชนกันที่ระดับฐานข้อมูล) |
| ชำระเงิน | เงินสด (ปุ่มธนบัตรด่วน + เงินทอน), QR PromptPay พร้อมยอด (สร้างในเครื่อง ใช้ได้แม้ออฟไลน์), บัตร (อ้างอิงสลิป EDC), ส่วนลด (ผู้จัดการขึ้นไป) |
| ใบเสร็จ | พิมพ์ใบเสร็จอย่างย่อขนาด 80mm ผ่าน `window.print()` |
| ออฟไลน์ | บิลขายหน้าร้าน "บันทึกลงเครื่องก่อน แล้วค่อยซิงค์" (IndexedDB) — ส่งซ้ำได้ไม่เกิดบิลซ้ำ, บิลที่เซิร์ฟเวอร์ปฏิเสธถูกเก็บให้ตรวจ ไม่หาย |
| กะ | เปิดกะพร้อมเงินทอนตั้งต้น, ปิดกะเทียบเงินสดที่ควรมีกับที่นับได้ |
| ผู้ใช้/สิทธิ์ | owner / manager / cashier, JWT, ยกเลิกบิล/รายการ/ส่วนลดเฉพาะผู้จัดการ |
| ประวัติ | audit log ทุกการยกเลิกบิล ยกเลิกรายการ ส่วนลด และราคาไม่ตรงตอนซิงค์ออฟไลน์ |
| รายงาน | ยอดขายรายวัน, จำนวนบิล, เฉลี่ยต่อบิล, รายชั่วโมง, เมนูขายดี, แยกตามวิธีชำระ |
| จัดการ | เมนู/หมวดหมู่/บาร์โค้ด, โต๊ะ, พนักงาน, ชื่อร้าน + PromptPay ID, เพิ่มสาขา (owner) |

## ฟีเจอร์ใน Phase 2 — Inventory & BOM (เมนู "คลัง")

| ส่วน | รายละเอียด |
|---|---|
| วัตถุดิบ | หน่วยฐาน กรัม / มล. / ชิ้น (เก็บเป็นจำนวนเต็ม), จุดสั่งซื้อ, SKU — กรอกเป็น กก./ลิตร ได้ ระบบแปลงให้ |
| สูตรอาหาร (BOM) | ปริมาณวัตถุดิบต่อจาน เช่น ข้าว 120 g หมู 100 g ไข่ 1 ฟอง |
| หักสต็อกอัตโนมัติ | เมื่อบิลถูกชำระ (ทั้งบิลโต๊ะและบิลออฟไลน์ที่ซิงค์เข้ามา) ในทรานแซกชันเดียวกับการชำระ — ส่งซ้ำไม่หักซ้ำ, สต็อกไม่พอก็ยังขายได้ (แสดง "ติดลบ") |
| รับเข้า | หลายรายการต่อใบ, ผู้ขาย, ราคารวมจริง, วันหมดอายุ → ต้นทุนเฉลี่ยถ่วงน้ำหนักอัตโนมัติ |
| เบิกใช้ / ของเสีย | ต้องระบุเหตุผล (หมดอายุ, เน่าเสีย, ทำหก…), ไม่ให้เบิกเกินคงเหลือ, ของเสียบันทึก audit log |
| โอนระหว่างสาขา | ตัดต้นทางตามต้นทุนเฉลี่ย รับเข้าปลายทางด้วยมูลค่าเดียวกัน |
| ตรวจนับ | กรอกยอดที่นับได้ เห็นผลต่างทันที ระบบปรับยอดและเก็บประวัติการนับ |
| คงเหลือ | มูลค่าสต็อก, รายการต่ำกว่าจุดสั่งซื้อ, ล็อตใกล้หมดอายุ 7 วัน |
| ต้นทุน & กำไร | ต้นทุนต่อจาน, กำไรขั้นต้นต่อเมนู (เตือน < 30%), รายงานรายวันเพิ่ม ต้นทุนขาย / กำไรขั้นต้น / มูลค่าของเสีย |
| ประวัติ | สมุดบัญชีสต็อก (ledger) ทุกการเคลื่อนไหว พร้อมคงเหลือหลังรายการ กรองตามวัตถุดิบ/ประเภท |

│  │  ├─ src/reports/       รายงานรายวัน (+ ต้นทุนขาย/กำไรขั้นต้น)
│  │  ├─ src/inventory/     วัตถุดิบ, สูตร, รับเข้า/เบิก/ของเสีย/โอน/ตรวจนับ
│  │  │  └─ costing.ts      ตรรกะต้นทุนถัวเฉลี่ย + BOM (+ unit test)
│  │  └─ scripts/smoke.mjs  ทดสอบ API ทั้งเส้นทางหลัก
│  └─ web/            React + TypeScript + Vite + Tailwind (PWA)
│     ├─ src/lib/offline.ts    คิวออฟไลน์ + แคชเมนู
│     ├─ src/lib/promptpay.ts  สร้าง payload Thai QR PromptPay (+ unit test)
│     ├─ src/lib/units.ts      แปลงหน่วย กก./ลิตร ↔ หน่วยฐาน (+ unit test)
│     └─ src/pages/            หน้าขาย, โต๊ะ, บิล, กะ, คลัง, รายงาน, จัดการ, ซิงค์

## เริ่มใช้งาน (เครื่องพัฒนา)

ต้องมี Node.js 20+ และ Docker

```bash
npm install
npm run db:up                         # PostgreSQL + Redis
cp apps/api/.env.example apps/api/.env
# แก้ JWT_SECRET ใน apps/api/.env เป็นสตริงสุ่มยาว ≥ 24 ตัว เช่น: openssl rand -hex 32
npm run seed                          # สาขา MAIN, ผู้ใช้ owner, โต๊ะ T1–T8, เมนู + วัตถุดิบ + สูตรตัวอย่าง
npm run dev:api                       # http://localhost:3000/api
npm run dev:web                       # http://localhost:5173
```

เข้าสู่ระบบด้วย `owner` / `ChangeMe!2026` (หรือค่าที่ตั้งใน `SEED_OWNER_PASSWORD`) แล้ว **เปลี่ยนรหัสผ่านทันที** ที่ จัดการ → พนักงาน
จากนั้นตั้ง PromptPay ID ที่ จัดการ → ตั้งค่าร้าน และเปิดกะที่เมนู "กะ" ก่อนเริ่มขาย
ถ้าจะใช้ระบบสต็อก ให้ "รับเข้า" วัตถุดิบตั้งต้นที่เมนู คลัง → รับเข้า (หรือ ตรวจนับ ครั้งแรก) เพื่อให้มียอดคงเหลือและต้นทุน

## ทดสอบ

```bash
npm test                              # unit test: เงิน, ต้นทุนสต็อก, กันเดารหัส (api) · PromptPay, หน่วย, คิวออฟไลน์ (web)

```

## ฐานข้อมูลและ migration

แอปรัน migration ที่ค้างให้อัตโนมัติตอนเริ่ม (เมื่อ `DB_SYNC=false` ซึ่งเป็นค่าแนะนำ)

```bash
# แก้ entity แล้วสร้าง migration ใหม่ (ต่อกับฐานข้อมูลที่ migrate ล่าสุดแล้ว)
npm run migration:generate -w apps/api -- src/migrations/AddSomething
npm run migration:run -w apps/api       # รันเอง (ปกติแอปรันให้ตอนเริ่ม)
npm run migration:check -w apps/api     # ตรวจว่า entity กับ migration ตรงกัน (CI รันทุกครั้ง)
```

> ฐานข้อมูลพัฒนาที่เคยสร้างด้วย `DB_SYNC=true` ให้สร้างใหม่ หรือคง `DB_SYNC=true` ต่อเฉพาะเครื่องพัฒนา

## ความปลอดภัย

- เปลี่ยนรหัสผ่าน / ปิดใช้งานพนักงาน → เซสชันเดิมทุกเครื่องหลุดทันที (ไม่ต้องรอโทเค็นหมดอายุ)
- ใส่รหัสผิด 5 ครั้งต่อบัญชี → ล็อกบัญชีนั้น 15 นาที (และกันไล่เดาหลายบัญชีจาก IP เดียว)
- ข้อมูลซ้ำ / อ้างอิงผิด / ตัวเลขเกินขอบเขต ตอบเป็น 4xx พร้อมข้อความไทย ไม่ทำให้ API ล่ม
- บิลออฟไลน์ที่เก่าเกิน 7 วันถูกปฏิเสธ (กันนาฬิกาเครื่องผิด/ลงบิลย้อนหลัง) และไปอยู่หน้า "การซิงค์" ให้ผู้จัดการตัดสินใจ
- รายงาน → "ประวัติที่ต้องตรวจสอบ": ยกเลิกบิล/รายการ, ส่วนลด, ราคาขายออฟไลน์ไม่ตรง, ของเสีย, แก้สูตร พร้อมผู้ทำ

## ก่อนขึ้น Production

- ใช้ `DB_SYNC=false` (migration) — ห้ามเปิด `DB_SYNC=true` กับฐานข้อมูลจริง
- อยู่หลัง reverse proxy ให้ตั้ง `TRUST_PROXY=1`
- ตั้ง `JWT_SECRET` ใหม่, เปิด HTTPS (PWA/Service Worker และ `crypto.randomUUID` ต้องการ secure context)
- ตั้ง `CORS_ORIGINS` ให้ตรงโดเมนจริง และสำรองฐานข้อมูลอัตโนมัติ
- ตั้งค่าสูตรให้ครบทุกเมนูที่ต้องการติดตามต้นทุน — เมนูที่ไม่มีสูตรจะไม่หักสต็อก
- QR PromptPay ใน Phase 1 ให้พนักงานตรวจยอดเงินเข้าก่อนยืนยัน — การยืนยันอัตโนมัติผ่าน Payment Gateway อยู่ใน Phase 3
