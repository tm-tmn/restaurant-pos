## หลายร้าน (multi-tenant)

- ฐานข้อมูลเดียว ทุกตารางมี `"tenantId"` ค่าเริ่มต้น `app_tenant_id()` = `NULLIF(current_setting('app.tenant_id', true), '')::uuid`
- ทุกตารางเปิด RLS: policy `tenant_isolation` ให้อ่าน/เขียนเฉพาะ `"tenantId" = app_tenant_id()`; ตาราง `tenants` อ่านได้เฉพาะแถวตัวเอง และ `pos_app` เขียนไม่ได้
- ทุกครั้งที่แอปยืม connection จาก pool (`common/tenant-db.ts`) จะตั้ง `role = pos_app` และ `app.tenant_id` ตามบริบทของงาน
  (`AsyncLocalStorage` ใน `common/tenant-context.ts`) และจำไว้บน connection เพื่อไม่ต้องตั้งซ้ำ
  - คำขอที่ล็อกอิน: JWT มี `tid` → AuthGuard ตรวจผู้ใช้ในนามร้านนั้น → `TenantInterceptor` รัน handler ในบริบทร้านนั้น
  - ไม่มีบริบท = มองไม่เห็นอะไร เขียนไม่ได้ (fail-closed)
  - โหมด system (กลับเป็นเจ้าของตาราง) ใช้เฉพาะจุดที่ต้องหาว่าเป็นร้านไหนก่อน: รหัสร้านตอนล็อกอิน, โทเค็น QR โต๊ะ/บัตรคิว, webhook — คืนแค่ `tenantId` แล้วทำงานต่อในบริบทร้าน
- foreign key ของ PostgreSQL ไม่สน RLS → trigger `enforce_same_tenant` ตรวจว่าคอลัมน์อ้างอิง (branchId, productId, tableId, …) เป็นของร้านเดียวกัน
- ค่า unique ที่เป็นของร้าน (รหัสสาขา, ชื่อผู้ใช้, SKU, บาร์โค้ด, ชื่อวัตถุดิบ) เป็น unique ต่อร้าน; โทเค็นสุ่ม (QR, คิว) และเลขธุรกรรมยัง unique ทั้งระบบ
- สร้างร้าน: `src/tenants/provision.ts` (ใช้ทั้ง CLI `tenant:create` และ seed) — แอปปกติสร้างร้านไม่ได้
- ทดสอบ: `scripts/tenants.mjs` ตรวจทั้งผ่าน API และตรงที่ฐานข้อมูล (role pos_app)

## Real-time

```
แก้ข้อมูล (API ตัวใดก็ได้) ──commit──► trigger notify_pos_change → NOTIFY pos_events {"b": branchId, "t": "orders,kitchen"}
                                                           │ (API ทุกตัว LISTEN)
                                         RealtimeListener รวมสัญญาณ 100ms → RealtimeGateway → ห้อง b:<branchId> (Socket.IO)
                                                           │
                              หน้าเว็บ (lib/live.ts) → invalidate React Query ตามหัวข้อ → โหลดผ่าน REST ตามปกติ
```
- ต่อ WebSocket ด้วย JWT เดียวกับ API; ส่งแค่ชื่อหัวข้อ ไม่ส่งข้อมูล — สิทธิ์และ RLS ยังตรวจที่ REST ทุกครั้ง
- ต่อไม่ได้/หลุด → หน้าจอกลับไปโหลดเป็นระยะ (ครัว 4 วิ, รอยืนยัน 5 วิ, คิว 5 วิ); ต่อได้ → โหลดสำรองทุก 30–60 วิ
- หลาย API instance ได้โดยไม่ต้องมี Redis (ทุกตัว LISTEN จาก PostgreSQL)

## หลักการสำคัญ

**เงินเป็นจำนวนเต็มสตางค์ทุกที่** — ทั้งฐานข้อมูล API และหน้าเว็บ แปลงเป็นบาทเฉพาะตอนแสดงผล
`calcTotals` / `settlePayments` (apps/api/src/common/money.ts) เป็นจุดเดียวที่คำนวณยอดและตรวจการชำระ

**Snapshot ราคา** — `order_items` เก็บชื่อและราคา ณ เวลาขาย แก้เมนูภายหลังไม่กระทบบิลเก่า

**Idempotency** — ทุกบิลมี `clientId` (UUID ที่เครื่องสร้าง) และ unique `(branchId, clientId)`
เครื่อง POS จึงส่งซ้ำได้ไม่จำกัดโดยไม่เกิดบิลซ้ำ

**ความถูกต้องเมื่อทำงานพร้อมกัน**
- เพิ่มรายการ/ชำระ/ยกเลิก ล็อกแถวออเดอร์ (`SELECT … FOR UPDATE`) ในทรานแซกชัน
- partial unique index: โต๊ะละ 1 บิลที่สถานะ `open`
- เลขที่บิล `สาขา-YYYYMMDD-NNNN` จากตัวนับรายวันแบบ atomic (`INSERT … ON CONFLICT … RETURNING`)

## สต็อกและต้นทุน (Phase 2)

ตาราง: `ingredients` · `recipe_items` (BOM) · `stock_levels` (คงเหลือต่อสาขา) · `stock_movements` (ledger) · `stock_counts`

**ปริมาณเป็นจำนวนเต็มหน่วยฐาน** (กรัม/มล./ชิ้น) และ **มูลค่าเป็นจำนวนเต็มสตางค์**
ต้นทุนเฉลี่ย = `valueSatang / qty` คำนวณสด ไม่เก็บแยก จึงไม่มีทศนิยมสะสม (apps/api/src/inventory/costing.ts)

| เหตุการณ์ | ปริมาณ | มูลค่า |
|---|---|---|
| รับเข้า | + | + ราคาที่จ่ายจริง (ถัวเฉลี่ย) |
| ขาย / เบิก / ของเสีย / โอนออก | − | − ตามต้นทุนเฉลี่ย (ตัดหมดพอดี = มูลค่า 0 ไม่มีเศษ) |
| โอนเข้า | + | + มูลค่าเท่าที่ต้นทางตัดออก |
| ตรวจนับ | = ยอดที่นับ | ตามต้นทุนเฉลี่ยเดิม |

- **การขายไม่ถูกบล็อก** เมื่อสต็อกในระบบไม่พอ — ยอดติดลบได้ (มูลค่า 0) และเมื่อรับเข้าภายหลัง จะชดเชยส่วนที่ติดลบก่อน
- เบิก / ของเสีย / โอน **ห้ามเกินคงเหลือ**
- หักวัตถุดิบใน **ทรานแซกชันเดียวกับการชำระเงิน** ทั้ง `pay` และ `syncOne` — บิลซ้ำจาก clientId เดิมไม่หักซ้ำ
- ล็อกแถว `stock_levels` เรียงตาม `ingredientId` (และ `branchId` สำหรับการโอน) เพื่อกัน deadlock — ทดสอบยิงขาย 20 บิลพร้อมกันแล้วยอดตรง
- ต้นทุนขาย (COGS) ของวัน = ผลรวมมูลค่า movement ประเภท `sale` ของบิลที่ชำระในวันนั้น
- วันหมดอายุเก็บต่อใบรับเข้า (ยังไม่ใช่ FIFO ต่อล็อต) ใช้แจ้งเตือนล็อตใกล้หมดอายุ

## QR สั่งอาหาร, ครัว, คิว (Phase 3)

```
 มือถือลูกค้า ──/t/<token>──►  PublicController (ไม่ล็อกอิน, จำกัดอัตรา ต่อ IP และต่อโต๊ะ)
                                  │  ราคามาจาก DB เสมอ · เพดานรายการรอยืนยัน · idempotent ด้วย submissionId
                                  ▼
                       order_items.status = pending ──(พนักงานยืนยัน)──► active + sentToKitchenAt ──► จอครัว (kitchenStatus)
```

- **โทเค็นโต๊ะ** `dining_tables.qrToken` (128 บิตสุ่ม) เป็นสิทธิ์เดียวของหน้าลูกค้า — เปิดได้เฉพาะโต๊ะนั้น เห็นเฉพาะบิลที่เปิดของโต๊ะนั้น (ไม่มีข้อมูลชำระเงิน/พนักงาน/สต็อก/sku/barcode) หมุนได้ทันที
- **`pending` ไม่นับยอด** — ทุก query เดิมที่กรอง `status='active'` (คำนวณยอด, ชำระ, หักสต็อก, รายงาน) จึงไม่เห็นรายการที่ยังไม่ยืนยันโดยอัตโนมัติ; ชำระ/สร้าง QR จ่ายจึงถูกบล็อกจนกว่าจะยืนยันหรือปฏิเสธ
- **เปิดบิลโต๊ะพร้อมกัน** (ลูกค้า/พนักงาน/ลูกค้าหลายคน) → unique index `uq_open_order_per_table` ตัดสิน ฝั่งที่แพ้ retry แล้วเข้าไปต่อบิลเดิม
- **แจ้งเตือนพนักงาน/จอครัว** ใช้ polling (5 และ 4 วินาที) — เรียบง่ายและทนเน็ตสะดุด; ถ้าต้องการ real-time จริงให้เปลี่ยนเป็น SSE/WebSocket ภายหลัง
- **คิว** `queue_tickets` เลขรันต่อวันต่อสาขาแบบ atomic (`queue_counters`), เปลี่ยนสถานะด้วยการล็อกแถว กันเรียก/จัดโต๊ะซ้อน; หน้าสาธารณะเห็นเฉพาะตั๋วของตัวเองผ่านโทเค็น

## การชำระ PromptPay อัตโนมัติ (Phase 3)

`payment_intents` = คำขอชำระหนึ่งครั้ง ตรึงยอด (และส่วนลดที่ผู้จัดการอนุมัติ) ณ ตอนสร้าง · อายุ 15 นาที

```
สร้าง intent (ยอดจากบิลใน DB) ──► แสดง QR ──► gateway ยิง webhook ──► ตรวจลายเซ็น ──► confirm()
                                                                                          │
   ล็อกบิล → ล็อก intent (ลำดับเดียวกับ "พนักงานกดชำระ" กัน deadlock)                      ▼
   ยอดโอน = ยอด intent? · บิลยัง open? · ยอดบิลเท่าตอนสร้าง QR? · ไม่มีรายการรอยืนยัน?
        ใช่ทั้งหมด ──► payCore() ชำระ + หักสต็อก + ปิด QR อื่นของบิล (ทรานแซกชันเดียว) ──► intent=paid
        ไม่ตรงข้อใด ──► intent=review + audit `payment.review` (ไม่ปิดบิล) ──► ผู้จัดการตรวจ/คืนเงิน
```

- **Idempotent:** `txnId` unique — gateway ยิงซ้ำ/พร้อมกันได้ ปิดบิลครั้งเดียว (ทดสอบยิง 8 ครั้งพร้อมกัน)
- **บิลเปลี่ยนหลังสร้าง QR** (เพิ่ม/ยกเลิก/ยืนยันรายการ) หรือบิลถูกจ่ายด้วยวิธีอื่นแล้ว → intent ที่ค้างถูก `cancelled`; เงินที่โอนมาทีหลังเข้าสู่ `review`
- **webhook** `POST /api/payments/webhook` (เปิดเมื่อ `PAYMENT_PROVIDER=webhook` + `PAYMENT_WEBHOOK_SECRET`)
  - headers: `x-timestamp` (ms, คลาดได้ ±5 นาที), `x-signature` = hex(HMAC-SHA256(secret, `${timestamp}.${rawBody}`))
  - body: `{ "intentId": "<uuid>", "txnId": "<เลขธุรกรรมจาก gateway>", "amountSatang": 12345, "status": "paid" }`
  - ตอบ 200 `{result: paid | duplicate | review | ignored}`, 401 ลายเซ็นผิด, 404 ไม่พบ intent, 409 txnId ซ้ำข้าม intent
- **ยังไม่ได้ทำ:** adapter ของผู้ให้บริการรายใดรายหนึ่ง (แปลง payload/ลายเซ็นของเขามาเป็นสัญญาข้างต้น และเรียก API สร้าง charge/QR ของเขาแทน QR PromptPay ที่ระบบสร้างเอง) — ต้องใช้บัญชี sandbox ของผู้ให้บริการที่เลือก
- **การขายกลับบ้านหน้าร้านแบบออฟไลน์** ยังยืนยัน PromptPay ด้วยมือ (ไม่มีบิลในระบบให้ผูก intent)

## จุดต่อยอดที่เตรียมไว้

- `tenants` + `branches` มีแล้ว → Phase 4 เพิ่มราคา/เมนูกลางต่อร้าน และราคาต่อสาขา
- Redis ใน docker-compose ยังไม่ถูกใช้ (ตัวจำกัดอัตราอยู่ในหน่วยความจำ; real-time ใช้ LISTEN/NOTIFY ของ PostgreSQL) — จะจำเป็นเมื่อรันหลาย API instance (ตัวจำกัดอัตรา/ล็อกอิน) หรือเพิ่มงานเบื้องหลัง เช่น ตรวจสอบยอดย้อนหลังกับ gateway
